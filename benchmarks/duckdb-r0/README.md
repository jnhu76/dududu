# DuckDB R0 closure protocol (E5)

Preparation for the #578 R0 DuckDB native baseline on the E5 host: what the
dataset is, what the SQL oracle asserts, how the stable output hash is taken,
and how I/O exposure is observed. **No performance measurement exists yet** —
A/A pairs and any timed run belong to the serial measurement lane. This file
freezes the protocol so those runs need no ad-hoc decisions.

Reuses the existing R0 infrastructure (PR #1): the pinned submodule, the
SHA-scoped `duckdb_native` build and the official benchmark harness. Nothing in
this directory re-implements a bridge or parser.

## Dataset

Generated by the official harness, not by a custom script:
`benchmark/tpch/parquet/parquet_projection_direct.benchmark` runs
`CALL dbgen(sf=1, suffix='_normal')` and
`COPY lineitem_normal TO '${BENCHMARK_DIR}/lineitem.parquet'`. In the pinned
v1.5.6 source `BENCHMARK_DIR` is the constant `duckdb_benchmark_data`
(`benchmark/interpreted_benchmark.cpp:108`,
`benchmark/include/benchmark_runner.hpp:27`), resolved under the runner's
root dir — so the file lands in the ignored
`build/duckdb-bench/duckdb_benchmark_data/lineitem.parquet` and never inside
the submodule (verified after generation: submodule porcelain clean).

Per-run dataset identity to record:

```bash
stat -c '%s %n' build/duckdb-bench/duckdb_benchmark_data/lineitem.parquet
sha256sum   build/duckdb-bench/duckdb_benchmark_data/lineitem.parquet
```

Determinism check (once per baseline): regenerate with the CLI into a scratch
file and compare hashes —

```bash
cd build/duckdb-bench && ../../build/duckdb-native/<sha>/duckdb -c \
  "CALL dbgen(sf=1, suffix='_regen'); COPY lineitem_regen TO 'duckdb_benchmark_data/lineitem-regen.parquet' (FORMAT PARQUET);"
sha256sum duckdb_benchmark_data/lineitem.parquet duckdb_benchmark_data/lineitem-regen.parquet
```

Equal hashes confirm dbgen + the parquet writer reproduce the dataset
byte-for-byte on this host; unequal hashes are a finding to record, not to
hide. Delete the scratch copy after the check.

## SQL Query Oracle and stable output hash

`oracle.sql` holds four deterministic queries over the dataset: exact
DECIMAL/INTEGER arithmetic only (no DOUBLE aggregates), every multi-row result
totally ordered by the unique `(l_orderkey, l_linenumber)` pair or aggregated
to one row, so repeated runs cannot vary by row order. q1/q4 are whole-table
scalar identities, q2 is the TPC-H Q1 aggregate shape grouped and ordered by
`(l_returnflag, l_linestatus)`, q3 exercises the sorted projection path.

```bash
cd build/duckdb-bench
mkdir -p oracle-out/run1 oracle-out/run2
for r in run1 run2; do
  sed "s|oracle-out/|oracle-out/$r/|g" ../../benchmarks/duckdb-r0/oracle.sql > /tmp/oracle-$r.sql
  ../../build/duckdb-native/<sha>/duckdb < /tmp/oracle-$r.sql
done
sha256sum oracle-out/run1/*.csv oracle-out/run2/*.csv
```

STABLE when each `qN.csv` hashes identically across the two runs. Record the
four hash pairs in the run manifest. The upstream `result` oracle of
`parquet_projection_direct.benchmark` (value `226829357828.867781`) is the
second, independent correctness check on the same dataset.

## I/O exposure observation (no timing)

Confirm where the bytes actually move before any adapter question is asked.
The v1.5.6 sync chain ends in `LocalFileSystem::Read` → `pread(2)`
(`docs/duckdb-stable-io-map.md` §1.1); the probe verifies that on this binary:

```bash
cd build/duckdb-bench
strace -f -y -e trace=openat,pread64,read,close -c -o io-count.txt \
  ../../build/duckdb-native/<sha>/duckdb -c \
  "SELECT SUM(l_extendedprice * (1 - l_discount) * (1 + l_tax)) FROM read_parquet('duckdb_benchmark_data/lineitem.parquet');"
# per-size distribution (warm page cache, second run):
strace -f -y -e trace=pread64 -o io-trace.txt \
  ../../build/duckdb-native/<sha>/duckdb -c "<same query>"
grep -o 'pread64([^,]*, ' io-trace.txt  # fd filter, then:
awk -F', ' '/pread64/ {print $3}' io-trace.txt | sort | uniq -c | sort -rn | head
```

Record: which file descriptors are opened (`-y` prints paths), the count of
`pread64` calls, the size distribution, total bytes, and the delta between the
first (cold-ish) and second (warm) run — the warm-run byte count through the
external file cache and page cache is the baseline adapter must-beat-blindness
flagged in `docs/duckdb-stable-io-map.md` §1.4. Counts and sizes are
observations, not measurements; latency percentiles from strace are discarded.

A cold-cache observation needs `drop_caches` (root) and is out of prep scope:
the prep sudo is scoped to installing measurement tools. `PR_SET_CLOEXEC`-style
alternatives do not exist for the page cache; if the measurement lane needs a
cold protocol it needs an explicit owner decision, same as the buffered fio
case.
