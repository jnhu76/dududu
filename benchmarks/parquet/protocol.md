# R1 standalone Parquet × Sluice — benchmark protocol

This round answers three falsifiable questions with a real Parquet reader
and no DuckDB involvement:

1. What I/O requests does the Apache Parquet C++ reader actually issue?
2. How much overhead does a native I/O wrapper add over Arrow's own file
   implementation for the same decode?
3. When `pread` is replaced by `sluice::blocking::read_at`, do performance,
   CPU cost and request behavior change repeatably?

No true-async claim is in scope. Sluice's `blocking::read_at` is a
completed-return synchronous call on the caller thread; everything here is
synchronous by construction and is only ever described as such.

## Arms

| Arm | Name | I/O implementation | Role |
|---|---|---|---|
| P0 | arrow native | `arrow::io::ReadableFile` | native baseline |
| P1 | native wrapper | custom `RandomAccessFile` + POSIX `pread` | adapter-cost control |
| P2 | sluice direct | same adapter + `sluice::blocking::read_at` | experiment arm |

P1 and P2 are literally the same `AdapterFile` over two interchangeable
`IoBackend` implementations (`experiments/parquet/src/backend_native.cpp` vs
`src/backend_sluice.cpp`). The reader cannot observe any difference except
the backend. Each backend TU contains exactly one byte-moving primitive:
P1's TU references `pread` and nothing else; P2's TU references
`sluice::blocking::read_at` and has no `pread` symbol at all (see
`results/r1/read-path-evidence.txt` for the nm/strace/fault-injection
provenance chain). Neither arm can fall back to the other.

## Reader and workload configuration (frozen)

* Arrow/Parquet 23.0.1 (Ubuntu `resolute` archive packages `23.0.1-9`),
  Google Benchmark 1.9.1 (`1.9.1-1build1`, shipped as a debug-built system
  library — uniform across arms, but it inflates absolute constants),
  GCC 15.2.0, CMake 4.2.3, Ninja 1.13.2, Release.
* Sluice: submodule `8fdcd99c5f9a42dadfe5aa0c095bf96c756aeb01`, `noliburing`
  profile, installed SDK consumed through `cmake/Sluice.cmake`
  (`Sluice::core`); no Sluice source change.
* Reader: `parquet::arrow::FileReaderBuilder`, unbuffered stream (default),
  **`pre_buffer=false` for every arm and every capture**. Arrow's default
  pre-buffering coalesces a full scan into one whole-file `ReadAt`, which
  would hide the request pattern this experiment observes. The setting
  lives in one place (`include/dududu/parquet/reader_config.hpp`) so arms
  cannot drift.
* Workloads, identical phase boundaries on every arm
  (`src/runner.cpp`): `open_meta` (builder open + T1 metadata walk or T2/T3
  reader build), `read` (the `ReadTable` call only), `verify` (oracle
  digest, measured separately, never inside a timed loop).
* T1 is metadata-only by construction and is never reported as a scan.
  T2 projects columns {1,4} inside the reader (trace: 13 requests / 1.1 MB
  vs 43 requests / 6.1 MB for the full scan on the small fixture — the
  projection demonstrably prunes).

## Datasets

Generated by `parquet_fixture` (fixed seed `0xD4D4D420261020`; every cell a
pure function of `(row, column-tag)`), uncompressed, written once per host
into the ignored `build/parquet-data/`. Their identity authority is not the
sidecar the generator writes next to them — both live under mutable
`build/` — but the frozen records committed with the evidence
(`results/r1/manifest-{small,medium}-none.json`): a dataset is admitted
only if its bytes and size still match that record.

| dataset | bytes | sha256 |
|---|---|---|
| small | 6118918 | `c2debb4c16228e5b66c9fbfa75e543b1ecff5e3b90b075db2ef1098a5e9eb3bb` |
| medium | 181966794 | `6116e69cf20a89b7ca8a23e4d4dbd7d3759225a68e379d4776b3727bf3c05af6` |

Schema (7 columns): `id` int64 sequential, `shuffle` int64 non-monotonic,
`i32_null10` int32 ~10% nulls, `f64_null5` double ~5% nulls, `text` utf8
0..24 chars, `wide` utf8 0..192 chars, `flag_null25` bool ~25% nulls.
Row groups alternate in size (small: 6000/10000×3+2000; medium:
160k/140k alternating) so column chunks vary in length. Generation time
never enters any sample.

## Sampling protocol

`bash benchmarks/parquet/run-bench.sh both` runs, in order:

1. build verification (untimed) — the three tools (`parquet_fixture`,
   `parquet_trace`, `parquet_bench`) are rebuilt before anything runs, so a
   stale executable from an earlier checkout either recompiles or stops the
   protocol instead of being measured under a newer receipt;
2. generate or verify datasets (untimed) — a dataset is admitted only if it
   hashes to the digest and size of the frozen r1 record
   (`results/r1/manifest-<name>-none.json`); anything else (missing,
   mutated, drifted — including a dataset that drifted together with its
   sidecar) regenerates once, and a regenerated dataset that still misses
   the frozen record is a hard error;
3. capture the request trace from an untimed diagnostic P1 run, plus a P2
   capture; `validate-trace.sh` (jq, independent of the C++ parser) then
   checks every line is valid JSONL and the two arms' request lists are
   identical;
4. write the provenance manifest
   (`build/parquet-results/run-manifest.txt`: `DUDUDU_SHA`, `SLUICE_SHA`,
   profile, SDK prefix, toolchain, repetitions, kernel, the SHA-256 of the
   three binaries and the staged Sluice libraries, dataset and trace
   digests) — only after the artifacts it names exist and verify, so an
   empty build can never produce a manifest without its artifact lines;
5. warm-up pass — full benchmark, results discarded (its only job is to
   make the sampled pass warm-cache);
6. sampled pass — Google Benchmark, `--benchmark_repetitions=10`,
   `--benchmark_min_warmup_time=2`, arms registered interleaved per workload
   so P0/P1/P2 run back-to-back; every pass is admitted by
   `validate-results.sh` (exact expected roster, 10 clean samples with
   dense repetition indices and positive times per benchmark, no
   `error_occurred` anywhere, and a full-entry closure check: every
   `(name, run_type, aggregate_name)` triple must belong to the roster, so
   ghost aggregates, duplicates and mislabeled aggregates fail admission;
   mean/median aggregate times must be positive, stddev/cv non-negative —
   an all-equal sample set is zero-variance, not broken) before its numbers
   count — a partial or errored pass aborts the protocol, an admitted pass
   appends its raw JSON digest to the manifest;
7. `summarize.sh` emits per-benchmark mean/median/CV and the attribution
   ratios.

The protocol scripts carry negative-first self-tests that run with the
suite as CTest `parquet.trace.jsonl`, `parquet.bench.admit` and
`parquet.bench.protocol` (18 + 20 + 30 cases): each gate must be seen
rejecting the malformed shapes it exists to stop, including the
truncated-header trace the serializer bug once produced, an aggregate
outside the roster, a dataset that drifted together with its sidecar, and
a manifest-less empty build.

Two documented deviations from the strictest reading of paired-run
discipline: (a) repetitions within one benchmark execute consecutively —
Google Benchmark runs registration order per benchmark, so arms alternate
per workload but not per repetition; arm samples are therefore not paired,
the residual run-order bias is not independently quantified, and the
CV-based resolution rule in `results-schema.md` is a descriptive
heuristic, not a bound on that bias, a confidence interval or a
significance test. Both passes (warm + sampled) are kept as artifacts.
(b) The oracle's NaN canonicalization is the standard quiet-NaN bit
pattern `0x7ff8000000000000` (changed from the original zero-pattern so a
NaN-to-+0.0 decode bug cannot hide; no fixture emits NaN, the rule is
future-proofing).

Cache protocol: warm OS page cache only. Nothing drops caches (no root,
no `sync`-as-invalidation). Cold cache is a separate experiment that has
not been admitted here.

Metrics per benchmark: wall/CPU time per repetition with mean/median/CV
aggregates, plus per-iteration counters (open_meta_ms, read_ms, rows,
cells, io_calls, requested/returned bytes, read_errors). P0 has no
transparent I/O hook point (wrapping it would stop it being the native
baseline), so its request profile comes from the diagnostic trace runs and
`strace`, not from per-iteration counters; this is disclosed per row rather
than fabricated.

## Attribution (each ratio stands alone; never summed)

```
Wrapper Tax        = T(P1) / T(P0) - 1
Sluice Effect      = T(P2) / T(P1) - 1
End-to-End Change  = T(P2) / T(P0) - 1
```

## I/O-only replay

The captured trace (one JSON Lines file: header + one line per
`ReadAt(offset, requested, returned)`) is replayed through each backend
separately: every request is re-executed against the real file, every
returned byte is consumed through an FNV-1a checksum, and the backend must
return exactly the captured byte count. Replay explains I/O cost only and
is never presented as a Parquet decode. A lying trace entry is detected and
fails the replay.

## Correctness admission (hard gate before any number)

`ctest` labels `parquet`: `parquet.contract`, `parquet.oracle`,
`parquet.trace` — see the commit `test(parquet): establish decoding and
fault oracles` for the oracle and negative-control inventory. A benchmark
number from an arm that has not matched P0's oracle digest is not a
result; in this round all three arms are admitted on T1/T2/T3 equivalence
plus the fault, corruption, truncation, fake-backend and concurrency
controls.

## Host disclosure

Verified host is Ubuntu 26.04 on WSL2 (kernel 6.18.54.1-microsoft-standard,
8 cores, 15 GB). Numbers from this host are correctness-and-exploration
evidence for the synchronous path; they are not promoted to native-Linux
production conclusions, and no cold-cache or native-NVMe claim is made.
