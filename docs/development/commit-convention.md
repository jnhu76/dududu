# Commit and PR title convention

dududu uses one repository-wide commit header format:

```text
<type>(<scope>): <subject>
```

Breaking changes use:

```text
<type>(<scope>)!: <subject>
```

Pull-request titles follow exactly the same rule.

The checker is `tools/check-commit.sh` (Bash + git only). Its contract is
defined negative-first by `tools/tests/check-commit-test.sh`. Lefthook
(`lefthook.yml`) enforces the rule locally at `commit-msg` and `pre-push`;
GitHub Actions (`.github/workflows/repo-policy.yml`) enforces the PR title.

## Allowed types

Only one primary type per commit:

| Type | Use it for |
| --- | --- |
| `feat` | A new capability (adapter, tool, experiment arm) |
| `fix` | A real bug fix |
| `refactor` | Structure change with no intended behavior change |
| `perf` | Performance-oriented implementation or optimization |
| `test` | Tests, executable evidence, oracles, negative controls |
| `build` | Build system, dependency, toolchain, linking, packaging |
| `ci` | CI/workflow behavior itself |
| `docs` | Documentation-only changes |
| `chore` | Repository maintenance that fits no other type |
| `revert` | An intentional revert |

Do not combine types:

```text
ci feat: add decoder          # wrong
chore/fix(repo): fix decoder  # wrong
test+fix(sdk): fix decoder    # wrong
```

If one cohesive change touches implementation plus a little documentation or
CI glue, use the type of the primary change. Split commits when the changes
have independent purposes.

## Scope

A scope is required. Scopes are lowercase kebab-case and describe a real
responsibility domain:

```text
repo      sdk       cmake     duckdb
adapter   bench     oracle    uring
docs      ci
```

Do not use roadmap, phase or experiment labels as scopes — the phase is the
PR/round context, not a responsibility:

```text
r0    d2    phase-1    stage-2    round-3    sprint-x    milestone-y
```

(The checker rejects `^[rd][0-9]+$` and the `phase/stage/round/step/
milestone/sprint` families outright.)

A scope is required so that `git log --oneline` shows ownership without
reading bodies.

## Subject

- begins with a lowercase letter or digit;
- states the action/result, imperative preferred;
- no trailing full stop (`.` or `。`);
- no trailing whitespace;
- keeps the whole header at 72 characters or fewer.

```text
feat(adapter): add native filesystem wrapper     # good
feat(adapter): Added the wrapper.                # wrong
```

The body and footers are unrestricted. `BREAKING CHANGE:` footers work as in
Conventional Commits; use `!` only for an intentionally breaking contract
change. Issue references belong in the body (`Refs #12`), not the subject.

## Merge commits

`--range` skips merge commits (two or more parents) with an explicit `SKIP:`
line. Their subjects are generated by git/GitHub, not authored. Everything
else in the range — including the first line of each commit, verbatim — is
validated. Already-merged `main` history is never re-judged: only
`base..head` is ever inspected.

## Automated gates

Local (Lefthook, see `lefthook.yml`):

1. `commit-msg` — validates the message being written, blocks the commit on
   violation. Never rewrites the message.
2. `pre-commit` — `git diff --cached --check` only.
3. `pre-push` — sequential, fail-fast:
   1. checker self-test;
   2. every commit the push would publish (`tools/push-range.sh`, which
      rebuilds the pushed set because lefthook does not forward the pre-push
      ref lines — it fails hard when the range is undeterminable);
   3. whitespace check over the same commits;
   4. the Sluice-only CMake/CTest gate, only when the push touches build
      files, C++ sources, tests, tools, hooks or submodule gitlinks.

Canonical manual run (always executes the complete gate — never a vacuous
pass):

```bash
lefthook run pre-push --all-files
```

CI (`.github/workflows/repo-policy.yml`) runs one minimal Ubuntu job: the
checker self-test plus the PR-title check, producing **Repository Policy
PASS**. It has no submodules, no C++, no cache and no artifacts; it is
deliberately not a build or correctness verdict.

## Bypassing

A push with `--no-verify` is not machine-checked anywhere; CI would still
reject a non-conforming PR title. Fix headers in place (`git commit
--amend`, `git rebase -i`) instead of pushing around the gate. Bootstrapping
the very first push to a brand-new remote (no baseline to diff against) is
the one accepted `LEFTHOOK=0 git push ...` case.

## Why this design

- **Local-first:** the machine that can compile and test produces the build
  and correctness evidence (see `AGENTS.md`); CI stays a cheap policy check.
  Waiting minutes for a runner to re-learn what the local gate already
  proved buys nothing.
- **Lefthook, not Husky/pre-commit frameworks:** a single static Go binary
  with one YAML config covers all three hooks; no Node/Python runtime enters
  the toolchain, matching the "no unnecessary tooling" rule in `AGENTS.md`.
- **Bash checker, not commitlint:** the validation rules are ~30 lines of
  POSIX-adjacent Bash and run in milliseconds; commitlint would import the
  entire npm ecosystem for the same verdict. The single `validate_header`
  function is shared by all entry points, so the hook, CI and the push gate
  can never disagree.
- **Negative-first tests:** the suite in `tools/tests/check-commit-test.sh`
  was written before the checker and fails against a missing or permissive
  checker; a green run is meaningful only because red runs exist.
- **Conservative push detection:** lefthook consumes the pre-push ref lines,
  so `tools/push-range.sh` reconstructs the pushed set from the `git push`
  command line and git state, and FAILS when it cannot. The alternative —
  validating a hardcoded range like `origin/main..HEAD` and going green —
  would silently miss force-pushes, multi-ref pushes and missing-baseline
  pushes.

The governing principle:

> **Type says what the commit does to the repository; scope says which
> responsibility domain it changes.**

Neither field encodes roadmap stage, experiment number, or campaign status.
