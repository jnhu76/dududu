# Commit and PR title convention

dududu uses one repository-wide commit header format:

```text
<type>(<scope>): <subject>
```

Breaking changes use:

```text
<type>(<scope>)!: <subject>
```

Pull-request titles follow exactly the same rule.

The checker is `tools/check-commit.sh` (Bash + git only). Its contract is
defined negative-first by `tools/tests/check-commit-test.sh`. Lefthook
(`lefthook.yml`) enforces the rule locally at `commit-msg` and `pre-push`;
GitHub Actions (`.github/workflows/repo-policy.yml`) enforces the PR title.

## Allowed types

Only one primary type per commit:

| Type | Use it for |
| --- | --- |
| `feat` | A new capability (adapter, tool, experiment arm) |
| `fix` | A real bug fix |
| `refactor` | Structure change with no intended behavior change |
| `perf` | Performance-oriented implementation or optimization |
| `test` | Tests, executable evidence, oracles, negative controls |
| `build` | Build system, dependency, toolchain, linking, packaging |
| `ci` | CI/workflow behavior itself |
| `docs` | Documentation-only changes |
| `chore` | Repository maintenance that fits no other type |
| `revert` | An intentional revert |

Do not combine types:

```text
ci feat: add decoder          # wrong
chore/fix(repo): fix decoder  # wrong
test+fix(sdk): fix decoder    # wrong
```

If one cohesive change touches implementation plus a little documentation or
CI glue, use the type of the primary change. Split commits when the changes
have independent purposes.

## Scope

A scope is required. Scopes are lowercase kebab-case and describe a real
responsibility domain:

```text
repo      sdk       cmake     duckdb
adapter   bench     oracle    uring
docs      ci
```

Do not use roadmap, phase or experiment labels as scopes — the phase is the
PR/round context, not a responsibility:

```text
r0    d2    phase-1    stage-2    round-3    sprint-x    milestone-y
r0a   r-0   phase1     stage0     step-1
```

(The checker rejects `r`/`d` plus a number, optionally hyphenated or
letter-suffixed, and the `phase/stage/round/step/milestone/sprint` families
with or without a numeric/hyphen suffix.)

A scope is required so that `git log --oneline` shows ownership without
reading bodies.

## Subject

- begins with a lowercase letter or digit;
- states the action/result, imperative preferred;
- no trailing full stop (`.` or `。`);
- no trailing whitespace;
- keeps the whole header at 72 characters or fewer.

"Header" means the first physical line, exactly as written — the checker
never joins a wrapped first paragraph the way `git log --format=%s` does, so
keep the subject on one line and let the body carry the detail.

```text
feat(adapter): add native filesystem wrapper     # good
feat(adapter): Added the wrapper.                # wrong
```

The body and footers are unrestricted. `BREAKING CHANGE:` footers work as in
Conventional Commits; use `!` only for an intentionally breaking contract
change. Issue references belong in the body (`Refs #12`), not the subject.

## Merge commits

`--range` skips merge commits (two or more parents) with an explicit `SKIP:`
line. Their subjects are generated by git/GitHub, not authored. The
`commit-msg` hook does the same: while a merge is in progress (`MERGE_HEAD`
exists), a message starting with `Merge ` is accepted as-is — a deliberately
coarse exemption, since `--range` skips merge commits entirely and telling
git's generated text from an authored one is not reliable at hook time. Everything
else in a range — including the raw first line of each commit, verbatim — is
validated. Already-merged `main` history is never re-judged: only
`base..head` is ever inspected.

## Automated gates

Local (Lefthook, see `lefthook.yml`):

1. `commit-msg` — validates the message being written, blocks the commit on
   violation. Never rewrites the message.
2. `pre-commit` — `git diff --cached --check` only.
3. `pre-push` — sequential, fail-fast:
   1. checker self-test;
   2. every commit the push actually publishes (`tools/push-range.sh`,
      fed by Git's own pre-push ref/SHA stream through lefthook's
      `use_stdin`; an empty stream is `NO_NEW_COMMITS`, malformed data or an
      unresolvable object is a hard failure). A new remote ref validates
      everything **not** reachable from the immutable pre-policy boundary
      below — inherited R0 history is grandfathered, new commits are not;
   3. whitespace check over the same commits;
   4. the Sluice-only CMake/CTest gate, only when the push touches build
      files, C++ sources, tests, benchmarks, tools, hooks or submodule
      gitlinks.

Manual run. It invokes every pre-push command, but step 4 still decides from
the paths the resolved ranges touch; a docs-only run skips CMake/CTest, and
that skip is not a pass. A manual run has no push stream, so the commit and
whitespace steps validate the current branch against its tracking/baseline
ref (use `bash tools/push-range.sh --range BASE HEAD` to check another range):

```bash
lefthook run pre-push --all-files
```

Complete manual gate on any range, including docs-only (this is the explicit
build-step override; with the config present the run cannot be a vacuous
pass — a branch that deletes this file falls outside machine enforcement,
exactly like a `--no-verify` push):

```bash
DUDUDU_FORCE_BUILD_GATE=1 lefthook run pre-push --all-files
```

The two tool suites that back the gate are plain Bash and run standalone:

```bash
bash tools/tests/check-commit-test.sh   # header policy, negative-first
bash tools/tests/push-range-test.sh     # push-set resolution scenarios
```

CI (`.github/workflows/repo-policy.yml`) runs one minimal Ubuntu job: the
checker self-test plus the PR-title check, producing **Repository Policy
PASS**. It has no submodules, no C++, no cache and no artifacts; it is
deliberately not a build or correctness verdict. Note that the workflow
executes the checker from the PR tree, so a PR that edits both the checker
and its self-test can satisfy CI; a policy check that must resist that needs
branch protection on `tools/` or a base-branch copy of the checker, which is
out of scope for R0.1.

## Bypassing

A push with `--no-verify` is not machine-checked anywhere; CI would still
reject a non-conforming PR title. Fix headers in place (`git commit
--amend`, `git rebase -i`) instead of pushing around the gate. A first push
to a brand-new remote is checked like any other new ref: Git reports a
zero remote SHA, and the gate validates every commit not reachable from
the immutable pre-policy boundary, so no bootstrap bypass is needed.

### The pre-policy boundary

Commits that predate this convention are grandfathered, never rewritten and
never re-judged. `tools/push-range.sh` pins the exemption to one fixed
commit — the R0 main tip `6e5f5c6db08f5b6780e13d92f357c65cdc865538` — and
only for the cases where no narrower base is provable (a new remote ref, or
a remote object absent locally): it validates `<boundary>..<tip>`, i.e.
exactly the commits that are **not** already reachable from the boundary.
A branch cut from any pre-policy commit therefore pushes cleanly on its
first attempt, while a new commit — or a whole unrelated orphan root — is
still checked, because neither is reachable from the boundary. The boundary
is deliberately a SHA, not a moving ref such as `origin/main`: a moving
base would silently exempt whatever main happens to contain at push time.
If the boundary object is missing locally (e.g. a shallow clone), the gate
falls back to validating the entire history — a false rejection, never a
silent pass.

## Why this design

- **Local-first:** the machine that can compile and test produces the build
  and correctness evidence (see `AGENTS.md`); CI stays a cheap policy check.
  Waiting minutes for a runner to re-learn what the local gate already
  proved buys nothing.
- **Lefthook, not Husky/pre-commit frameworks:** a single static Go binary
  with one YAML config covers all three hooks; no Node/Python runtime enters
  the toolchain, matching the minimal-toolchain rule (rule 8) in `AGENTS.md`.
- **Bash checker, not commitlint:** the validation rules are ~30 lines of
  POSIX-adjacent Bash and run in milliseconds; commitlint would import the
  entire npm ecosystem for the same verdict. The single `validate_header`
  function is shared by all entry points, so the hook, CI and the push gate
  can never disagree.
- **Negative-first tests:** the suite in `tools/tests/check-commit-test.sh`
  was written before the checker and fails against a missing or permissive
  checker; a green run is meaningful only because red runs exist.
- **Authoritative push data, not a Git emulator:** Git writes one
  `<local ref> <local sha> <remote ref> <remote sha>` line per ref it will
  publish to the pre-push hook. lefthook replays that stream to
  `tools/push-range.sh`, which validates exactly those SHAs. Options,
  `remote.<name>.push` recipes, explicit/wildcard/negative refspecs,
  matching refspecs (`:` and `+:`), `--all` and `--mirror` are therefore
  resolved by Git itself. An earlier version reconstructed the push set from
  the `git push` command line; three review rounds found real pushes it
  misparsed (global options, configured refspecs, mirror namespaces,
  matching refspecs), so the reconstruction was removed rather than
  extended. Deletions carry a zero local SHA and validate nothing; a new
  remote ref or an object absent locally validates everything not reachable
  from the immutable pre-policy boundary (see above) — the inherited R0
  history is exempt by reachability from a fixed SHA, not by skipping roots
  or trusting `origin/main`, so a genuinely new commit or orphan root cannot
  hide behind the exemption. Malformed or unresolvable push data is a hard
  failure, never a fallback to the current branch. Manual runs have no push
  stream and check the current branch (or `--range`); that path cannot hide
  a published ref because it is only used when nothing is being pushed.

The governing principle:

> **Type says what the commit does to the repository; scope says which
> responsibility domain it changes.**

Neither field encodes roadmap stage, experiment number, or campaign status.
